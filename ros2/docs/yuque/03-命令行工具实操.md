# 03 命令行工具实操：从 `ros2 run` 到 `ros2 param dump`

> ⚠️ **本文的终端输出全部标注了"预期输出"**：本机没有 ROS2（见 [01](01-工作空间与包结构.md) 开头的说明），
> 我没有伪造截图。这些输出是按 Humble 官方文档 + 消息定义推导出的**应该长什么样**，
> 真实输出请跑 `ros2/scripts/verify_stack.sh`（会把每一节的结果写进 `docs/verify_report_*.txt`）。
> 我把"预期"两个字写在每一处，是为了让读者知道**哪一行是我亲眼见过的、哪一行是我推的**。

## 0. 一句话总结

ROS2 的命令行是**自解释**的：几乎每个子命令都支持 `-h`，而且**绝大多数 `-h` 输出就是一份可以照着敲的示例**。
我的习惯是"先 `ros2 <cmd> -h` 看一眼，再 `ros2 <cmd> <sub> -h`"，比翻文档快。

## 1. 启动：`ros2 run` 与 `ros2 launch`

```bash
ros2 run hello_cv_cpp camera_node          # 前台跑，Ctrl-C 退出
ros2 run hello_cv_cpp camera_node --ros-args -p fps:=10.0 -r image_raw:=/test/img
```

`--ros-args` 之后是**ROS 自己的参数解析**，不是程序的参数。三种最常用：

| 写法 | 作用 |
| --- | --- |
| `-p name:=value` | 改一个参数（`fps:=10.0`，注意 `:=`） |
| `-r old:=new` | 重映射话题/服务名（`image_raw:=/test/img`） |
| `--log-level DEBUG` | 打开调试日志（`--log-level camera_node:=debug` 只给某个节点） |

```bash
ros2 launch hello_cv_cpp full_pipeline.launch.py
ros2 launch hello_cv_cpp full_pipeline.launch.py threshold:=170 use_rviz:=true
ros2 launch hello_cv_cpp camera_detector.launch.py --show-args   # 列出可传的 launch 参数
```

`--show-args` 是我最喜欢的一个参数：不用读 launch 源码就知道能传什么。

预期输出（`full_pipeline.launch.py`，简略）：

```text
[INFO] [launch]: All log files can be found below /home/you/.ros/log/...
[INFO] [launch]: Default logging verbosity is set to INFO
[INFO] [camera_node-1]: process started with pid [41231]
[INFO] [detector_node-2]: process started with pid [41232]
[INFO] [tracker_node-3]: process started with pid [41233]
[INFO] [tf_lookup_node-4]: process started with pid [41234]
[camera_node-1]   [INFO] camera_node 启动：320x240 @ 30.0 Hz，frame_id=camera_link，QoS=reliable
```

## 2. 节点：`ros2 node`

```bash
ros2 node list
ros2 node info /camera_node
```

预期输出：

```text
/camera_node
/detector_node
/tf_lookup_node
/tracker_node
```

`ros2 node info` 是**最有用的单条命令**——它把一个节点的"全部对外接口"一次列清：

```text
/camera_node
  Subscribers:
  Publishers:
    /camera/image_raw: sensor_msgs/msg/Image
    /parameter_events: rcl_interfaces/msg/ParameterEvent
    /rosout: rcl_interfaces/msg/Log
  Service Servers:
    /camera_node/describe_parameters: rcl_interfaces/srv/DescribeParameters
    /camera_node/get_parameters: rcl_interfaces/srv/GetParameters
    /camera_node/set_parameters: rcl_interfaces/srv/SetParameters
    ...
  Service Clients:
  Action Servers:
  Action Clients:
```

两个观察：

1. **每个节点都自动有 6 个参数服务和一个 `/rosout` 发布者**，这是 `rclcpp::Node` 帮你建的。
   所以你写 1 行 `create_publisher`，`node info` 里其实是 3 个发布者。
2. 服务和话题**放在同一个命名空间里**（`/camera_node/...`）。节点名就是它的默认命名空间前缀，
   这也是 `ros2 param set /camera_node fps 10.0` 能对上号的原因。

## 3. 话题：`ros2 topic`

### 3.1 看有哪些、长什么样

```bash
ros2 topic list                 # 只要名字
ros2 topic list -t              # 带类型
ros2 topic info /camera/image_raw
ros2 topic info -v /camera/image_raw     # 带 QoS 与两侧端点
```

预期输出：

```text
$ ros2 topic list -t
/camera/image_raw [sensor_msgs/msg/Image]
/parameter_events [rcl_interfaces/msg/ParameterEvent]
/rosout [rcl_interfaces/msg/Log]
/vision/detection [hello_cv_interfaces/msg/Detection]
/vision/target_marker [visualization_msgs/msg/Marker]
/vision/track [hello_cv_interfaces/msg/Detection]
/tf [tf2_msgs/msg/TFMessage]

$ ros2 topic info /camera/image_raw
Type: sensor_msgs/msg/Image
Publisher count: 1
Subscription count: 1
```

`-v` 是我排查 QoS 问题的**唯一正确姿势**：

```text
$ ros2 topic info -v /camera/image_raw
Type: sensor_msgs/msg/Image
Publisher count: 1
Node name: camera_node
Node namespace: /
Topic type: sensor_msgs/msg/Image
Endpoint type: PUBLISHER
GID: 01.0f.3a...
QoS profile:
  Reliability: RELIABLE
  History (Depth): KEEP_LAST (10)
  Durability: VOLATILE
  Lifespan: Infinite
  Deadline: Infinite
  Liveliness: AUTOMATIC
  Liveliness lease duration: Infinite
Subscription count: 1
Node name: detector_node
QoS profile:
  Reliability: RELIABLE
  ...
```

两侧的 `Reliability` / `Durability` 必须**兼容**，否则连不上，而 ROS2 **不会报错**——
这个话题我在 [04](04-Topic与QoS.md) 里详细写。

### 3.2 看数据

```bash
ros2 topic echo /vision/detection              # 一帧一帧刷
ros2 topic echo /vision/detection --once       # 只打一条
ros2 topic echo /vision/detection --once --no-arr    # 关键：别把 data 数组铺开
ros2 topic hz /camera/image_raw                # 频率
ros2 topic bw /vision/detection                # 带宽
```

`--no-arr` 极其重要。`/camera/image_raw` 里 `data` 是 76800 个字节，`echo` 一下会刷屏几秒，
把前面有用的 `header.stamp` 全冲掉。加了 `--no-arr` 就变成 `data: <76800 bytes>`。

预期输出：

```text
$ ros2 topic echo /vision/detection --once
header:
  stamp:
    sec: 1729780000
    nanosec: 123456789
  frame_id: camera_link
found: true
cx: 213.4
cy: 96.7
area: 2151.0
confidence: 0.993
---
$ ros2 topic hz /camera/image_raw
average rate: 30.012
	min: 0.033s max: 0.034s std dev: 0.00041s window: 32
```

### 3.3 手动发一条（不用写发布者也能测）

```bash
ros2 topic pub --once /vision/detection hello_cv_interfaces/msg/Detection \
  "{header: {frame_id: camera_link}, found: true, cx: 160.0, cy: 120.0, area: 1020.0, confidence: 0.99}"
```

这条命令的价值：**验证"下游节点是好的"**。如果 `topic pub` 能让 `tracker_node` 动，
那问题一定在上游；反之问题在下游。调试时这个二分法省掉一半时间。

`-r 10` 可以按 10Hz 持续发：

```bash
ros2 topic pub -r 10 /vision/detection hello_cv_interfaces/msg/Detection "{found: true, cx: 160.0, cy: 120.0, area: 1020.0}"
```

## 4. 服务：`ros2 service`

```bash
ros2 service list                              # 全部服务
ros2 service list -t | grep hello_cv           # 只看自己的
ros2 service type /set_mode                    # 类型
ros2 service find hello_cv_interfaces/srv/SetTrackingMode   # 反查：谁提供这个类型
ros2 service call /set_mode hello_cv_interfaces/srv/SetTrackingMode "{mode: ema, alpha: 0.2}"
```

预期输出：

```text
$ ros2 service type /set_mode
hello_cv_interfaces/srv/SetTrackingMode

$ ros2 service call /set_mode hello_cv_interfaces/srv/SetTrackingMode "{mode: raw, alpha: 0.5}"
requester: making request: hello_cv_interfaces.srv.SetTrackingMode_Request(mode='raw', alpha=0.5)

response:
hello_cv_interfaces.srv.SetTrackingMode_Response(success=True, message='模式已切换为 raw')
```

非法输入也要试（这是我写 `verify_stack.sh` 时特意加的一条）：

```text
$ ros2 service call /set_mode hello_cv_interfaces/srv/SetTrackingMode "{mode: ema, alpha: 5.0}"
response:
hello_cv_interfaces.srv.SetTrackingMode_Response(success=False, message='alpha 必须落在 (0, 1] 区间内')
```

两个细节：

1. **服务是同步的**，命令行会**阻塞**等响应。节点没起时不是超时，是**一直等**——用 `Ctrl-C` 退出。
2. 参数的 YAML 里 `alpha: 5.0` 必须写成浮点。写 `alpha: 5` 也能解析（会当 int 再转 float），
   但如果字段是 `int32`，写 `5.0` 就会报类型不符。

## 5. 参数：`ros2 param`

```bash
ros2 param list                                  # 所有节点的所有参数
ros2 param list /detector_node                   # 只看一个节点
ros2 param get /detector_node intensity_threshold
ros2 param set /detector_node intensity_threshold 200
ros2 param dump /detector_node                   # 导出成 YAML（可以存成 params.yaml）
ros2 param describe /detector_node intensity_threshold   # 类型/范围/描述（如果有描述）
```

预期输出：

```text
$ ros2 param list /detector_node
  expected_area
  intensity_threshold
  max_area
  min_area
  qos_reliability
  use_sim_time

$ ros2 param get /detector_node intensity_threshold
Integer value is: 180

$ ros2 param set /detector_node intensity_threshold 200
Set parameter successful

$ ros2 param set /detector_node intensity_threshold 999
Setting parameter failed: intensity_threshold 必须落在 [0, 255]
```

最后那条失败**是我故意设计的行为**：`add_on_set_parameters_callback` 里拒绝非法值，
并回一个 `reason`。这让"参数"从"随便写"变成"有契约"。

`ros2 param dump` 的输出是**可以直接当参数文件用**的：

```yaml
/detector_node:
  ros__parameters:
    intensity_threshold: 200
    min_area: 200
    max_area: 50000
```

注意 key 是 `/detector_node`（带斜杠的**全限定名**）。这一条在 launch 里坑过我，见 [07](07-launch文件.md)。

## 6. 一次"我实际会敲"的完整流程

```bash
# 1) 起整条流水线
ros2 launch hello_cv_cpp full_pipeline.launch.py use_rviz:=false &

# 2) 确认节点齐了
ros2 node list

# 3) 确认话题通、频率对
ros2 topic hz /camera/image_raw        # 期望 ~30Hz
ros2 topic hz /vision/detection        # 期望 ~30Hz

# 4) 看一眼检测结果（别把 data 铺开）
ros2 topic echo /vision/detection --once --no-arr

# 5) 确认 TF 在发
ros2 topic hz /tf                      # 期望 >= 30Hz（camera_link + target 两个源）

# 6) 切一次跟踪模式
ros2 service call /set_mode hello_cv_interfaces/srv/SetTrackingMode "{mode: raw, alpha: 0.2}"

# 7) 热更新检测阈值，观察检测面积变化
ros2 param set /detector_node intensity_threshold 200
ros2 topic echo /vision/detection --once --no-arr

# 8) 把当前参数固化下来
ros2 param dump /detector_node
```

这条流程我写成了脚本 `ros2/scripts/verify_stack.sh`：它把每一步的**命令 + 真实输出**写进
`docs/verify_report_<时间戳>.txt`，一份报告就是一份可复核的证据链。

## 7. 几个救命的小技巧

| 场景 | 命令 |
| --- | --- |
| 忘了包名/可执行名 | `ros2 pkg executables \| grep hello` |
| 忘了消息字段 | `ros2 interface show hello_cv_interfaces/msg/Detection` |
| 想确认服务是谁提供的 | `ros2 service find <类型>` |
| 想确认参数是谁的 | `ros2 param list \| grep -B2 threshold` |
| 话题有数据但下游不触发 | `ros2 topic info -v` 看两侧 QoS |
| 节点闪退看不到日志 | `ros2 run ... --ros-args --log-level DEBUG` |
| 想验证"是不是下游坏了" | `ros2 topic pub --once` 手动喂一条 |
